# Organic Driven Development

ODD means Organic Driven Development in TaskSystem. Observable outcomes are
acceptance criteria; Observability-Driven is a separate optional capability.

1. Establish intent and authority. Explanation, investigation and proposals
   remain read-only. Do not reinterpret a question as permission to implement.
2. Inspect the existing behavior and conventions before proposing a change.
   Extend the existing seam when suitable; do not duplicate an implemented API.
3. Resolve named uncertainty with source evidence or authorized public research.
   Ask the owner about genuine product, scope, permission or risk decisions.
   Skipping, declining or a custom response does not silently authorize work.
4. Classify using understanding, risk and resumability, not file or line count.
   Unknown risk or unresolved uncertainty blocks implementation. Named security,
   data, contract, concurrency, delivery, external-effect or verification risk
   uses the formal route even when the diff is small.
5. Keep a bounded task record in the configured harness workspace. Preserve
   the original request, scope, classification rationale and actual evidence.
   For light work do not add specification/design/approval documents merely
   to imitate the formal route. Substantial or sensitive work uses SDD with
   explicit bindings, scenario ownership and approvals.
6. Implement the smallest coherent authorized unit. Reproduce behavior with
   a causal failing test when a deterministic runner exists. Report exceptions
   rather than inventing RED, a runner, a tool or proof. Run checks only with
   actual authorization; do not execute project-discovered scripts implicitly.
7. Review the complete diff and raw evidence. Obtain a fresh independent
   review or the explicit scoped owner waiver required by project policy.
   Close only the covered task; report failures, unknown impact and continuation.

Delegate only settled, bounded work when useful and supported by the host.
Pass immutable request/spec locators and runtime state rather than summaries
that alter requirements. A role or distinct context label is not authentication.
Neither the light route nor a successful test authorizes installation,
publication, paid models, destructive effects or the next task.

If required runtime gates are unavailable, state that limit and ask for the
missing capability. Never present an instruction as native tool interception.
